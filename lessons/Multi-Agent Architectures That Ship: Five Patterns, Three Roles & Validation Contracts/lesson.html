Multi-Agent Architectures That Ship: Five Patterns, Three Roles & Validation Contracts

Assemble agent teams that run for days — by separating who builds from who verifies, defining 'done' before any code exists, and putting the right model in each seat.

Overview

The bottleneck in software engineering is no longer intelligence — it is human attention. A team may have fifty features in the backlog and models capable of implementing all of them, but only enough bandwidth to supervise a few per day, because every task needs attention and every commit needs review. The interesting question becomes: what if a human decides what to build, and a system figures out how?

Multi-agent research is a mess of competing frameworks and terminology, so this lesson starts with a taxonomy that cuts through it — five communication patterns from which every multi-agent system is assembled. It then walks through one production architecture built from four of them, called missions, whose longest run lasted sixteen days.

The surprises are where the value is. Parallelism, the obvious way to go faster, made things worse and was abandoned for serial execution with narrow internal parallelism. Tests written by the agent that wrote the code turn out to confirm decisions rather than catch bugs, which forced validation to be redesigned around a contract written before implementation. And the whole orchestration lives in roughly 700 lines of prompt text rather than a state machine, specifically so the system improves when models improve instead of being obsoleted by them.

Key takeaways

  • Five patterns compose every multi-agent system: delegation, creator-verifier, direct communication, negotiation, and broadcast.
  • Direct communication (agents DMing each other with no coordinator) is the one to avoid — state fragments and there is no single source of truth.
  • Separate the agent that builds from the agent that verifies: the author has a cost bias toward its own code working, exactly why humans do code review.
  • A validation contract, written during planning before any code, defines correctness independently of implementation — often hundreds of assertions, each feature owning one or more.
  • Tests written after implementation are shaped by the code rather than the intent, so they confirm decisions instead of catching bugs.
  • Validate behaviour, not just code: a QA-style validator drives the running application through computer use, and that real-world execution — not token generation — consumes most of a mission's wall-clock time.
  • Structured handoffs (what was done, what was left, commands run with exit codes, issues found) are what let the system self-heal at milestone boundaries.
  • Serial execution with targeted read-only parallelism beat parallel workers: coordination overhead ate the speed gains while the error rate rose.
  • Planning, implementation, and validation reward different model strengths, and no single provider is best at all three — being model-agnostic means you are not capped by one family's weakest capability.
  • Keep orchestration in prompts and skills rather than a hard-coded state machine, so every model improvement makes the system better instead of obsolete.

The five multi-agent communication patterns

1:28

Delegation, creator-verifier, direct communication, negotiation, and broadcast — the primitives every framework is built from.

The multi-agent field is fragmented: everyone has their own framework, terminology, and opinions about what works. A simple taxonomy cuts through it, because every system is assembled from five communication patterns.

**Delegation** is one agent spawning another and receiving a result — a parent saying 'go figure out the database schema' and getting an answer back. It is the simplest form of multi-agent communication and what almost everyone implements first; sub-agents in coding tools are the common example.

**Creator-verifier** has one agent build something and a second check it. The point is separation of concerns: the agent that wrote the code carries a cost bias, because it wants that code to work. A fresh agent with fresh context is far more likely to find real issues — the same reason humans review each other's code rather than their own.

**Direct communication** is agents talking without a central coordinator, effectively DMing each other. It is hard to get right, because state fragments across those conversations and there is no single source of truth.

**Negotiation** is agents communicating over a shared resource — the same API, the same region of the codebase. It need not be adversarial; the best case is net positive-sum trading, where interacting agents find a genuine win-win.

**Broadcast** is one agent informing many: status updates, new context that applies to everyone, shared constraints. It is the least flashy pattern and it is critical for keeping a long-running task coherent.

Key points

  • Delegation: an agent spawns another and gets a result back. Simplest pattern, usually implemented first, e.g. sub-agents.
  • Creator-verifier: builder and checker are separate, because the author is cost-biased toward its own work succeeding.
  • Direct communication: no coordinator, agents message each other. Hard to get right — state fragments, no single source of truth.
  • Negotiation: coordination over a shared resource, ideally positive-sum rather than adversarial.
  • Broadcast: one-to-many information sharing. Unglamorous but essential to coherence over long runs.

Missions: four patterns in one workflow, three roles

4:12

Orchestrator plans, workers implement, validators verify — an ecosystem communicating through structured handoffs and shared state, not one long agent session.

Missions composes four of the five patterns — delegation, creator-verifier, broadcast, and negotiation — into a single workflow. Notably it omits direct communication, for the reason given above. You describe a goal, scope it through conversation, approve a plan, and the system executes for hours or days.

The crucial distinction is that a mission is not a single agent session. It is an ecosystem of agents communicating through structured handoffs and shared state, organised into three roles.

The **orchestrator** handles planning. When you describe what you want it acts as a sounding board, asks strategic questions, and probes unclear requirements. It produces a plan containing features, milestones, and a validation contract.

**Workers** handle implementation. A worker assigned a feature starts with clean context — no accumulated baggage, no degraded attention. It reads its spec, implements the feature, and commits via git, so the next worker inherits both a clean slate and a working codebase. That per-feature reset is what stops quality decaying as a run gets longer.

**Validators** handle verification. Most systems validate by running lint, type checks, and tests, perhaps with code review. Missions does all of that and also validates behaviour — not 'does the code look right?' but 'does this work end to end?' That is the difference that lets a run continue for days without drifting.

Key points

  • Missions composes delegation, creator-verifier, broadcast and negotiation — deliberately excluding direct communication.
  • You describe a goal, scope it conversationally, approve a plan; the system then executes for hours or days.
  • A mission is an ecosystem communicating via structured handoffs and shared state, not one long session.
  • Orchestrator: plans, interrogates requirements, and emits features, milestones and a validation contract.
  • Workers: one feature each with clean context, then commit via git so the next worker inherits a working codebase.
  • Validators: lint/types/tests and code review, plus end-to-end behavioural verification.

Validation contracts: define 'done' before writing code

6:15

Tests written after implementation are shaped by the code rather than the intent, so they confirm decisions instead of catching bugs.

This is the sharpest insight in the talk. You have probably seen the pattern: an agent builds a feature, writes tests, the tests pass, coverage is high — and the feature is still wrong. The reason is that the tests were shaped by the code, not by what the code was supposed to do. Stated plainly: **tests written after implementation don't catch bugs, they confirm decisions.** Build a system that validates itself that way and it will eventually drift, with a green suite the whole time.

The validation contract breaks that circularity by ordering. It is written during planning, before any code exists, and it defines correctness independently of implementation. For a complex project it can run to hundreds of assertions. Each feature is then assigned one or more assertions it must satisfy, with the invariant that the sum of all features covers every assertion.

Because the contract predates the code, no implementation choice can quietly redefine what counts as correct. An agent cannot weaken an assertion to make its work pass, the way it can weaken a test it also wrote. And because assertions are allocated to features up front, a feature that satisfies its own assertions but breaks another's is caught rather than absorbed.

Write assertions about observable behaviour, not internal structure. 'Posting a message makes it appear for every member of that channel without a reload' survives refactors; 'MessageService.post() calls broadcast()' does not.

Key points

  • Tests written after implementation are shaped by the code, so they confirm decisions rather than catching bugs.
  • The validation contract is written during planning, before any code, and defines correctness independently of implementation.
  • A complex project may have hundreds of assertions; each feature is assigned one or more.
  • The invariant: the sum of all features must cover every assertion in the contract.
  • Because the contract predates the code, an agent cannot weaken the definition of correct to make its own work pass.
  • Assert on observable behaviour rather than internal structure, so assertions survive refactoring.

Two validators, adversarial by design

6:57

A scrutiny validator runs the suite and spawns per-feature code review; a user-testing validator drives the live application like a QA engineer.

After each milestone of features, two kinds of validator run.

The **scrutiny validator** is the more traditional one. It runs the test suite, type checking, and lints, and — critically — spawns dedicated code review agents for each completed feature in that milestone. One reviewer per feature, rather than one reviewer squinting at an enormous diff.

The **user-testing validator** is the more interesting one, and it behaves like a QA engineer. It spawns the application and interacts with it through computer use or something similar: filling out forms, checking that pages render correctly, clicking buttons, and confirming that functional flows work holistically. This is what 'validate behaviour, not code' means concretely.

That step takes significantly longer than scrutiny, because the system is driving a live application rather than reading text. The consequence is counter-intuitive and worth internalising for capacity planning: **most of a mission's wall-clock time is spent waiting for real-world execution, not generating tokens.** Your throughput is bounded by how fast the application under test responds, so time and token spend decouple.

The property that makes both validators trustworthy is that neither has seen the code before. They are not invested in the implementation and have no stake in its succeeding — validation is adversarial by design. This is creator-verifier applied rigorously: fresh context is not an optimisation here, it is the entire source of the validator's credibility.

Key points

  • Scrutiny validator: test suite, type checking, lints, plus a dedicated code review agent per completed feature.
  • User-testing validator: spawns the app and drives it via computer use — forms, rendering, clicks, whole flows.
  • Behavioural validation takes far longer than static checks because it waits on a live application.
  • Most of a mission's wall-clock time goes to real-world execution rather than token generation, so time and cost decouple.
  • Neither validator has seen the code before, so validation is adversarial by design — fresh context is the source of its credibility.

Structured handoffs and self-healing

8:19

A worker does not just report 'done' — it writes down what happened, and the system corrects course at milestone boundaries.

For a system running many days, catching bugs is not enough; context must survive between agents. When a worker finishes a feature it fills out a structured handoff rather than declaring itself done.

The handoff records what was completed, what was left undone, which commands were run during that agent loop and what their exit codes were, what issues were discovered, and whether the worker abided by the procedures the orchestrator defined for it. That is a deliberately specific list, and each field earns its place: 'left undone' prevents silent partial work, exit codes give the next agent ground truth instead of a summary, and the procedures check surfaces an agent that quietly went its own way.

This is how the system self-heals. Errors get caught at milestone boundaries, corrective work is scoped into follow-up features, and the mission pulls itself back on track — as the talk puts it, not by hoping that agents remember what happened, but by forcing them to write it down and then actually address the issues. Progress is blocked while handoff issues remain unaddressed, so problems cannot be skipped past.

The longest mission run so far lasted sixteen days, longer than a full sprint, and thirty is thought feasible. That is only possible because of this structure: durable written state is what makes a run's length independent of any single agent's memory.

Key points

  • A handoff records: completed work, work left undone, commands run with their exit codes, issues discovered, and procedure compliance.
  • Exit codes give the next agent ground truth rather than a prose summary that may be wrong.
  • Errors surface at milestone boundaries, where corrective work is scoped into follow-up features.
  • Progress is blocked while handoff issues are unaddressed, so nothing gets skipped.
  • The longest run was 16 days, with 30 believed feasible — durable written state is what makes that possible.

Serial execution beats parallelism

9:00

Ten agents did not give ten times the throughput — they conflicted, duplicated work, and made inconsistent decisions until coordination overhead ate the gains.

The obvious way to go faster is parallelism: ten agents at once should mean ten times the throughput. They tried it, and for software development it does not work.

The failures are specific. Agents step on each other's changes. They duplicate work neither knows the other is doing. And most damagingly they make inconsistent architectural decisions, because each is choosing in ignorance of the others. The coordination overhead required to prevent all this ends up consuming the speed gains, and you burn tokens throughout.

So missions runs features **serially** — only one worker or validator active at any moment. Parallelism is retained where it is safe: within a feature, read-only operations such as searching the codebase or researching APIs run in parallel, and within validators, read-only work such as code review is parallelised across features. The shape is serial execution with targeted internal parallelisation.

On paper this is slower. In practice the error rate drops dramatically, and for tasks running over many days that correctness compounds — every avoided inconsistency is one that does not have to be discovered and unpicked later. The general principle worth extracting: parallelise reads freely, serialise writes. Conflicts come from concurrent mutation, so the operations that only observe are exactly the ones that are safe to fan out.

Key points

  • Parallel workers conflict: they overwrite each other, duplicate work, and make inconsistent architectural decisions.
  • Coordination overhead consumes the speed gains while tokens are still being burned.
  • Missions runs features serially — one worker or validator at a time.
  • Read-only operations are parallelised inside a feature (codebase search, API research) and inside validators (code review).
  • Slower on paper, but the error rate falls sharply and correctness compounds across a multi-day run.
  • The transferable rule: parallelise reads, serialise writes.

The right model in each seat

11:03

Planning wants slow careful reasoning, implementation wants fast code fluency, validation wants precise instruction following — and no one provider is best at all three.

Everything above assumes you are using the right model in each role, because the three roles reward genuinely different strengths. Planning benefits from slow, careful reasoning. Implementation benefits from fast code fluency and creativity. Validation benefits from precise instruction following. No single model — and no single provider — is best at all three.

Operating a system like this therefore demands a new skill, which the team calls 'droid whispering': mentally modelling how different models behave, where each fails, how those failures compound over a multi-day run, and then deliberately choosing which model sits in which seat. Their engineer Theo produced the defaults from building the prototype, but teams are encouraged to customise them to their project.

One configuration choice deserves highlighting: validation may use a **different provider entirely**, so the verifier is not biased by the same training data as the implementer. That is creator-verifier taken to its logical end — you want the checker's blind spots to be different from the builder's, not merely its context.

This is the structural argument for a model-agnostic architecture: you are only as strong as your weakest link, and if you are locked into one provider you are constrained by that family's weakest capability. As models specialise, putting the right model in the right seat compounds. The relationship also runs the other way — validation contracts and milestone checkpoints supply enough structure that missions run successfully even on open-weight models that are not at frontier performance. Structure substitutes for raw capability.

Key points

  • Planning rewards slow careful reasoning; implementation rewards fast code fluency and creativity; validation rewards precise instruction following.
  • No single model or provider is best at all three, so the seats should be filled independently.
  • Use a different provider for validation so the verifier is not biased by the implementer's training data.
  • Locked into one provider, you inherit that family's weakest capability as your ceiling.
  • Structure substitutes for capability: contracts and checkpoints let missions succeed even with open-weight models.

Beating the bitter lesson: prompts, not state machines

14:27

Keep orchestration logic in text so the next model release improves the system instead of obsoleting it.

Everyone building multi-agent systems fears that the next model release will make their architecture obsolete overnight — the bitter lesson, which holds that general methods leveraging more compute beat hand-engineered structure. The design response was to require that the system get *better* with every model improvement.

Concretely, almost all orchestration logic lives in prompts and skills rather than a hard-coded state machine. How the system decomposes features and handles failures is expressed in roughly 700 lines of text, and four sentences of it can alter the execution strategy dramatically. Worker behaviour is driven by skills that the orchestrator defines per mission, so behaviour is customised per project rather than compiled in.

The only deterministic logic is deliberately thin, and it is focused on bookkeeping: running validation, and blocking progress when handoff issues have not been addressed. The division is clean — **missions ensure the discipline, models provide the intelligence** — and it is built on primitives models already understand, like AGENTS.md and skills.

Why this survives a model upgrade: a state machine encodes what today's models cannot do, so improvements make its branches dead weight. Prompt-expressed intent encodes what you want, so a more capable model simply executes it better. The deterministic layer, being pure bookkeeping, is orthogonal to capability and does not need revisiting either.

  • The fear: a new model release obsoletes your architecture. The requirement: the system must improve with every model improvement.

Production reality, and what it unlocks

13:06

A Slack clone built end to end: 60% of time and tokens on implementation, validation never passing first time, and half the final codebase being tests.

The numbers from building a Slack clone make the architecture concrete. Implementation consumed about 60% of both time and tokens. Validation **never succeeded on the first attempt** — follow-up features were almost always required, which is the clearest evidence that the QA loop is doing real work rather than rubber-stamping. The finished codebase was around 50% test code by line count, with roughly 90% coverage. Prompt caching was used heavily to offset the cost of such long runs.

Because a multi-day run cannot be supervised through a chat transcript, there is a dedicated view — mission control — showing how much of the project is complete, how much of the budget has been burned, what the active worker is doing right now, and the handoff summaries describing what validators discovered and how the plan is changing. That lets you either act as a project manager overseeing implementation, or step away entirely.

In production the enterprise uses cluster around prototyping features overnight, building internal tools quickly, running large refactors and migrations, ML research, and modernising codebases specifically so that agents are more productive in them.

The economics are what the whole talk builds toward. A team of five engineers that previously ran about ten work streams can run perhaps thirty, with the humans focused on architecture and product decisions rather than execution. And the codebase ends up *cleaner* than it started: the end-to-end tests, unit tests, skills, and structure that missions produce leave both agents and humans more productive afterwards — which is the opposite of the usual outcome when you optimise for speed.
